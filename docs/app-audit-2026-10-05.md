# App audit — October 5, 2026

The intended launch keeps concurrent personal and community +5 Fate rewards. The human accepts a roughly fortnightly reroll pace. Financial support now provides its Discord role only. A two-month launch grace period will bank newly earned personal/community overflow; it never moves existing balances. The existing normal Fate100 and Bank100 caps remain.

## Scope and evidence

Reviewed active command entry points, central dispatch, wallet and economy services, community/profile/Sanity rollout, scheduled jobs, supporter roles, seasonal maintenance, database/deployment isolation, and dependency inventory. Existing Spooky tests cover the detailed game receipts, replay, rollback, role/nickname guards and conservation. Added adversarial disposable-memory probes for legacy currency commands, birthdays and shop failure. All live inspections used read-only SQLite and Discord GETs. No real purchase, reset, historical clawback or game action was performed.

This is an application audit with focused executable probes, not a proof that every possible fault or dependency exploit is absent. Disabled old seasonal implementations are separated from current reachable paths. Live production still uses its independent deployment; source-only leveling/profile/Sanity changes are not presumed deployed there.

Evidence is ignored under `.runtime/app-audit`: `live-read-only.json`, `offline-probes.json`, dependency audit JSON for both runtimes, test logs, deployment manifest/backups and process verification. Live inspection includes private account IDs/names; those are deliberately omitted here.

## Financial-support changes

- Removed role-acquisition and daily +1 Banked Fate grants, and the reward-related support DMs.
- Removed supporter-only personal-level overflow and `/fate add-fate` Bank privilege. Financial status no longer changes wallet eligibility or reward size. Existing owner-admin grants remain unchanged pending the wider command audit.
- Removed `boosterTotal` from the User runtime model. The old database column is retained untouched as historical evidence with its existing default0; no destructive migration or counter reset.
- A legacy `creditBank(...,{countBoost:true})` call now fails before writing, protecting against an accidentally retained old grant path.
- New supporter monitor checks at startup and hourly using fresh paginated REST members and `premiumSinceTimestamp`. It scopes to the selected guild, detects stale/missing native booster roles, contains lookup failures and shares concurrent checks. It never changes balances or attempts to edit Discord's managed boost role.
- Production's configured role was verified as the native managed Server Booster role. Its one holder matches its one active Discord booster. Development uses an unrelated Developers test role, which is explicitly skipped as proof of payment. See [Discord's role metadata](https://docs.discord.com/developers/topics/permissions#role-object-role-tags-structure).

## Live balance findings

Production:80 stored accounts,44 current human guild members,10 eligible campaign players. Two eligible players are at the normal Fate cap; none are simultaneously at both Fate and Bank caps. No invalid normal-Fate/Bank balances, above-cap Bank balances, integrity errors or foreign-key violations were found.

Five production accounts have historical booster totals of at least50; the largest recorded lifetime total is415, and the sum is1199. These are cumulative counters, not current balances, payment evidence, or proof of an accidental grant. Legacy daily grants lack individual durable receipts, so the counter cannot reconstruct which points remain or distinguish erroneous awards from authorized historical awards. Current native role/status is consistent; that does not establish historical correctness. No automatic clawback is justified from these counters alone. Development contains a separate legacy-data copy and must not be used to infer current production reward history.

## Two-month overflow protection

`config/fate-overflow-grace.json` holds separate development/production windows. Both remain disabled with null dates until leveling launch is authorized/prepared. `launchWindow(actualLaunchInstant)` returns two Pacific calendar months, preserving wall time across DST and clamping month-end dates. Set the reviewed explicit startsAt/endsAt at rollout; do not restart the window on bot restart or config21 event reload.

At Fate98/Bank63, +5 yieldsFate100/Bank66. At Fate100/Bank99, +5 yieldsBank100 with4 uncredited because both balances are full. After the exact end boundary, ordinary overflow stops banking automatically. Existing above-cap legacy Bank is preserved rather than reduced. Supporter status does not affect this temporary policy. Existing balances are not transferred, doubled or clawed back.

Personal reward receipts/snapshots report actual banked/discarded overflow and add an explanatory note to level-up embeds/cards. Community reward receipts include each player's Bank before/after, actual credit and launch note; the community level announcement explains the temporary window if any reward banked overflow. Ordinary grants/shop purchases do not gain a general overflow exemption. Birthday/prize exceptional rewards retain their existing rules.
