## Interfaces and wiring

`services/spooky/lifecycle.js` exports `createLifecycle({ models, economy, playful, delivery, guildId, event, winnerSnapshots = null })` with `maintain(key)`. It uses root worker operations scoped to the configured event/guild. Runtime passes winnerSnapshots; cleanup, frozen winner proof and the closure marker commit together, then Discord projections reconcile outside the transaction. The phase comes from the economy transaction's clock, so a request queued before the boundary closes correctly if execution starts afterwards.

`createMaintenanceScheduler({ getService, event, clock, isReady, intervalMs, setTimer, clearTimer, onError })` exposes `start()`, `tick()` and `stop()`. Default cadence is one minute. Start performs an immediate tick. Deterministic keys are `maintenance:v<configVersion>:slot:<floor(epochMs/intervalMs)>` under the economy's event/guild scope. Repeated ticks/restarts in a slot replay saved DB work but still retry pending role/nickname delivery. A per-scheduler busy guard skips overlapping ticks; the economy still serializes root writes. Independent ticks in later slots are separate audited operations.

`runtime.startMaintenance(client)` creates one scheduler per client via a WeakMap. `app.js` attaches it to ready without changing the existing holiday job. While disabled, no timer is created, runtime models are not opened, and Discord is not contacted. The timer is unreferenced, readiness skips disconnected clients, invalidation stops it, and callers can explicitly `stop()` during shutdown. Stopping does not recall an in-flight network call. Errors are logged and a later tick can retry. Credentials/guild selection continue to use the existing runtime authority.
